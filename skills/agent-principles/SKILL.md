# Agent Operating Principles

大部分給 agent 的規則在講**怎麼省 token**或**怎麼跑流程**。
這份在講**怎麼不要犯同一種錯**。

每一條都來自實際發生過的失敗。**不是理論，是帳單。**

規則的形式固定：

> **原則** — 一句祈使句
> **它防的失敗** — 真的發生過的事
> **檢查** — 一個可以真的執行的動作

---

## 一、診斷

### 1.1 察覺自己在「換個做法再試一次」，就是漏了診斷

**它防的失敗**：使用者要背景音樂。做了三版全被否決 ——
失諧正弦、五聲音階琴音、低通和弦。每一版都是「換個做法再試」，
沒有一次停下來問「他到底要什麼」。第四次才發現需求是
「墊在真實環境音底下的襯底」，而那個需求從第一句話就在那裡。

**檢查**：第二次嘗試之前，寫下**至少兩個**候選根因，各自標明證據，
以及「看到什麼就能分辨是哪一個」。只想得到一個，代表你在確認猜測。

### 1.2 先看實際數據，不要沿用舊結論

**它防的失敗**：排程遲到的註解寫「實測穩定遲到 45-50 分」，
於是把時間往前挪 50 分抵銷。實際去查近八次 —— 遲到 53 到 124 分。
註解是三週前寫的，數字早就漂了。

而且真正的原因不是「會遲到」，是**排在整點**。同一個 repo 排在 `:45`
的那支穩定遲到 55-62 分。看了數據才看得出來。

**檢查**：任何「已知的常數」在拿來做決策前，跑一次量測。
註解與文件會過期，數字不會。

## 二、驗證

### 2.1 驗使用者會看到的東西，不是你方便驗的東西

**它防的失敗**：報告「字卡全部驗證通過，12 張全部對上旁白」。
驗的是 props JSON 裡的時間數字。使用者看完影片說「字卡沒出現」——
卡片確實有算出來，但字級只佔畫面 12%、停 4.6 秒，掃過去等於沒有。

**同一個錯犯了兩次**，兩天之內。第一次是長片，第二次是短片。

**檢查**：交付前問一句「使用者會從哪裡看到這個」，然後從那裡看一次。
影片就抽幀，網頁就開起來，API 就打一次。
**檢查中間產物只能證明中間產物是對的。**

### 2.2 靜默不等於成功

**它防的失敗**：背景指令回報 `exit=0`，於是報告「render 跑起來了」。
實際上指令用了相對路徑，工作目錄沒帶到，`exit 127` 直接死掉 ——
而我還在向使用者回報進度。

另一次是 render 的進度用 `\r` 原地更新，`grep` 一行都收不到，
log 檔看起來是空的，我以為還沒開始。

**檢查**：長時間工作要看**它產生的東西**（檔案有沒有長大、幀數有沒有增加），
不要只看它有沒有噴錯。以及：**過濾條件要能捕捉失敗，不是只捕捉成功。**
問自己「如果它現在崩了，我的過濾條件會噴出東西嗎」。

## 三、事實與記錄

### 3.1 「檔案裡沒寫」不等於「事情沒發生」

**它防的失敗**：發布記錄檔的 `published` 欄位全是 `null`，
於是推論「五支影片全都沒發布，瓶頸在發布不在品質」，
並據此建議使用者停下手邊的事去發片。

實際上早就照排程發出去了，當天已經是第二支。**記錄沒更新，而不是事情沒做。**

**檢查**：狀態檔的「空」有兩種意思，分不出來就問。
拿記錄當論據之前，先確認那份記錄最後一次被寫入是什麼時候。

### 3.2 結論要連著依據一起記，只記結論會被誤用

**它防的失敗**：說「重做橫式片頭要花兩次生成額度」。
理由是成品是直式的。但**原始素材本來就是橫式**，直式那版是後製合成的。
只看了結果，沒看它怎麼來的。

**檢查**：記錄一個限制時，一併記「我怎麼知道的」。
下一個人（或下一輪的你）才有辦法判斷它還成不成立。

## 四、遷移教訓

### 4.1 教訓有適用範圍，別無差別套用

**它防的失敗**：先前學到「prompt 裡寫飽和色名會生出螢光卡通色」，
所以在生一隻**本來就接近螢光橘**的動物時，加了 `NOT neon`。
結果顏色被壓成暗琥珀，跟真實物種不符。

前一個教訓的前提是「這動物其實不鮮豔，是模型誇張了」。
新案例的前提相反。**同一條規則，相反的情境。**

**檢查**：套用舊教訓前，說出它成立的前提，再確認新情境符不符合。
說不出前提，代表你記的是結論不是原理。

---

## 五、執行環境

### 5.1 背景與非互動指令一律用絕對路徑

**它防的失敗**：背景指令裡的 `cd` 沒有帶到，`./venv/bin/python` 找不到，
`exit 127`。而我以為它在跑，還回報了三分鐘進度。

**檢查**：任何不在你當前 shell 裡跑的東西 —— 背景任務、cron、CI、
另一個 process —— 路徑全部寫絕對的。

### 5.2 改預設值要把所有入口一起改

**它防的失敗**：把函式的預設參數從 55 改成 110，跑起來卻沒有變化。
因為 CLI 的 `argparse` 也有一個 `default=55`，把函式預設蓋掉了。
**改了等於沒改，而且數據看起來像是「這個改動沒效果」。**

**檢查**：改預設值後，grep 那個舊值。同一個東西常常有兩三個入口。

### 5.3 對應關係用明確的鍵，不要靠順序

**它防的失敗**：用「順序對應」寫了一張 id → 文案的表，整排位移一格，
七筆全部錯位，而且是成品產出後才被使用者看出來。

**檢查**：任何 A 對到 B 的地方，寫成 `{a: b}` 不要寫成兩個並列的 list。

## 六、迭代成本

### 6.1 重跑很貴的東西，攢著一起改

**它防的失敗**：一支影片重算了六次。每次只改一兩個參數，
每次要等三到十三分鐘。使用者中途問了四次「跑到哪了」。

**檢查**：動手之前先估「驗證一次要多久」。超過幾分鐘的，
把所有已知要改的東西一次改完再跑。
**同時也要有便宜的驗證路徑** —— 抽樣、預覽、只算三十秒，
把「錯了重來十三分鐘」變成「錯了重來一分鐘」。

### 6.2 接既有管線之前，先看它吃什麼資料

**它防的失敗**：規劃了整支長片的章節、鏡頭、素材，全部做完之後
才發現既有的剪輯管線是為短片寫死的，資料結構完全不相容。
那支檔案我在過程中開過兩次，兩次都只搜了關鍵字，沒看它的輸入格式。

**檢查**：要復用一支程式，先讀它的輸入與輸出結構，不要只搜關鍵字。

## 怎麼用這份

- **開工前**掃一次標題（十二條，三十秒）
- **卡住時**回來讀第一節
- **交付前**讀第二節
- **踩到新的坑**就加一條，格式照舊：原則 / 它防的失敗 / 檢查

**新增的條目必須來自真實發生的事。** 想像出來的原則沒有重量，
而且會把這份文件稀釋成又一個「最佳實踐清單」。
