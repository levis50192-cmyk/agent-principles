# 電梯維修管理系統：現況分析與地端化計畫

分析對象：GitHub 上功能最完整的電梯維修專案（含工單）。同帳號另有兩個程式副本與一個早期估價系統；前三者是同一套程式的複製版本，差異只在公司名稱、圖示與工單功能。

> 影片中的畫面是用示範資料跑出來的（假的客戶名稱與零件），沒有讀取任何真實客戶資料。

## 1. 系統現況

- **架構**：React 19 + Vite 的手機 App（PWA）→ Vercel（網站與 2 支 API）→ Supabase 雲端（Postgres 資料庫、Auth 登入、Storage 檔案）；AI 故障排除呼叫 Google Gemini。
- **使用者**：管理員、技師兩種角色，以「員工編號@公司網域 + 6 位 PIN」登入。
- **功能**：客戶（含電梯參數表照片）、工單（派工、現場照片、使用零件、客戶簽名）、估價單（稅率、議價加成、列印）、零件資料庫（匯入 813 筆）、領料申請與審核、領料統計、故障報告單（簽名、列印）、AI 故障排除、文件庫、員工管理、首頁（近 30 天待保養）。
- **程式規模**：106 處資料庫呼叫、10 處檔案儲存、9 處登入、1 處呼叫自家 API；2 支 Vercel 函式（`api/admin/employees.js`、`api/troubleshoot.js`）。

## 2. 資料離開公司的四個地方

| # | 位置 | 說明 |
|---|---|---|
| 1 | Supabase 資料庫 | 客戶、估價、工單、領料、故障報告 |
| 2 | Supabase Storage | 現場照片、簽名、參數表照片、文件庫 |
| 3 | Google Gemini | AI 排障每次最多送 40 筆歷史故障報告（含 `customer_name`）（`src/pages/faults/Troubleshoot.jsx`、`api/troubleshoot.js`） |
| 4 | 員工手機 | PWA 快取查詢結果 5 分鐘、檔案 30 天；`signOut` 只清掉 `supabase-cache`，`storage-cache` 仍留在裝置（`vite.config.js`、`AuthContext.jsx`） |

## 3. 需改進項目

### 高優先（資安與資料）

1. **權限只在畫面上擋。** `setup_schema.sql` 的規則多為 `to authenticated using (true)`，任何登入員工都能讀、改、刪全部資料；前端用 `isAdmin` 隱藏按鈕，技師直接呼叫 API 就能繞過。→ 依角色在資料庫授權、改軟刪除、加稽核紀錄。
2. **AI 排障外送客戶名稱。** → 地端化時改本機模型、去識別化，或先關閉。
3. **資料庫結構不完整。** `work_orders`、`work_order_parts` 在任何 SQL 檔都找不到（重置腳本 只有 10 張表，程式卻用到 12 張）。→ 搬家前先從現行資料庫匯出完整結構並納入版本控管。
4. **危險腳本。** 重置腳本 含 `DROP TABLE IF EXISTS public.customers CASCADE`。→ 移出專案或加防呆。
5. **沒有備份與還原。** 維護指南自己寫「免費版閒置 7 天會暫停」。→ 每日備份、定期還原演練。
6. **停用員工只在登入時檢查。** `signIn` 登入後才查 `is_active`，已發出的憑證仍可存取資料；資料庫規則沒有 `is_active` 條件。

### 中優先（維運與程式）

1. 6 位數 PIN、沒有失敗鎖定。
2. 同一套程式複製成多份，修一次要改三次。
3. 工單編號 `WO年月-隨機 3 碼`，一個月只有 900 種組合，可能重複。
4. PWA 快取規則寫死 `supabase.co` 網址，搬到本機後失效。
5. 沒有自動測試與 CI；README 仍是 Vite 範本；維護指南缺災難復原流程。
6. 列印版型在窄螢幕表格被擠壓（系統名稱逐字換行）。

### 建議新增（選配）

保養排程與到期提醒、離線建立工單、工單一鍵帶入估價單、匯出 Excel、客戶簽名加時間與裝置紀錄。

## 4. 地端化方案

| | A 自架 Supabase（Docker） | B 自建後端（Node + PostgreSQL） | C PocketBase |
|---|---|---|---|
| 程式修改 | 幾乎不用（換網址與設定） | 約 125 處改寫 | 資料、權限、登入都要改 |
| 資料搬遷 | `pg_dump` 直接還原 | 需轉換 | 需轉換 |
| 維運 | 中（約 10 個容器） | 低到中 | 低 |
| 時間 | 短 | 長 | 中 |

**建議：先採 A 上線，穩定後再視需要簡化。** 比較與工時為依程式碼規模的評估。

### 目標架構

公司內網一台主機：Caddy（HTTPS、內網憑證）→ 前端網站 + 自架 Supabase（Postgres、Auth、Storage、API）+ 小型 Node API（取代 Vercel 函式：員工管理、AI 排障）+ 本機 AI 模型（選配）；每日備份到 NAS／外接碟；UPS。外出技師經 VPN 連回，或限定公司內使用。不再使用 Vercel、Supabase 雲端、Google Gemini。

### 遷移步驟（預估 7–8 週）

1. 盤點與決策、主機採購或備機
2. 架設主機（Docker、自架 Supabase、HTTPS）
3. 匯出雲端資料庫與檔案，還原到本機
4. 程式調整：環境變數、快取規則、員工 API、AI 排障
5. 平行試跑 2 週，補權限規則與測試
6. 切換上線，員工改用內網網址、安裝憑證
7. 關閉雲端專案、刪除雲端資料、還原演練

## 5. 本機準備清單

假設約 30 人以下使用、檔案容量數百 GB 內。

- **硬體**：4 核心以上 CPU、16 GB 記憶體（建議 32 GB）、SSD 500 GB 以上；第二顆硬碟或 NAS 做備份、外接碟做每週離線備份；UPS；選配本機 AI 可用 16 GB VRAM 顯示卡或 CPU 小模型。
- **軟體**：Ubuntu LTS（或 Windows + WSL2）、Docker 與 Compose、Node.js 20+、Git、Caddy 或 Nginx、選配 Ollama。
- **網路**：固定內網 IP、內網網域、HTTPS 憑證（PWA 一定要 HTTPS）、把內網憑證安裝到員工手機與電腦、防火牆只開 443；外出技師用 WireGuard／Tailscale 等 VPN。
- **資安**：磁碟加密、最小權限、金鑰兩人保管、離職停用流程、日誌與稽核。
- **備份**：每日自動備份資料庫與檔案、每週離線一份、每季還原演練、備份也要加密。
- **人與文件**：維運負責人與代理人、操作手冊、緊急還原 SOP、更新排程、資料保存與刪除政策。
- 客戶資料若含自然人姓名、電話、地址，屬個人資料，保存與存取規範請由公司法務確認。

## 附：分析的限制

- 只讀了程式碼與 SQL 檔，沒有連到你們實際的 Supabase 專案，所以實際資料量、現行資料庫規則、使用人數都是推估。
- 「工單兩張表不在 SQL 檔」代表**程式碼庫**裡找不到，不代表雲端資料庫沒有。
- 工時與規格為建議值，需依實際情況調整。
